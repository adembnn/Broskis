# Recherche · performance et fluidité en écran scindé temps réel (Three.js)

Contexte : BROSKIS passe en 1v1 temps réel écran scindé (`plan/PIVOT-TEMPS-REEL.md`), un seul `WebGLRenderer`, 2 vues via `setViewport`/`setScissor`. Machine de démo : portable RTX 5060 double GPU, Chrome, 1080p, projecteur. Objectif : 60 i/s stables, zéro saccade pendant 2 min de démo live.

## 1. 15 règles concrètes, classées par gain probable pour NOTRE jeu

1. **Forcer le GPU NVIDIA dans Chrome (pas dans le code).** Sur un portable double GPU, Chrome choisit par défaut l'iPUC Intel pour économiser la batterie ; le passage forcé au GPU dédié via les réglages Windows (« GPU hautes performances » assigné à chrome.exe) ou `--force_high_performance_gpu` peut faire une différence de x2 à x4 sur les i/s. C'est déjà noté dans `quality.ts` (28 i/s sur Intel vs 64 sur NVIDIA mesurés). **Gain : le plus gros de tous**, et c'est un réglage machine, pas du code — à vérifier sur le PC de démo avant 18h, pas à corriger en JS. Sources : [Windows 11 Dedicated GPU for Web Browsing](https://www.needsomefun.net/windows-11-dedicated-gpu-browsing/), [Chromium issue 40668498](https://issues.chromium.org/issues/40668498).
2. **Un seul post-traitement pour les 2 vues, jamais 2 composeurs.** Rendre les 2 vues (`setViewport`+`setScissor`) dans la même cible du `EffectComposer`, puis un seul passage de bloom/vignette sur l'image complète — exactement ce que prévoit déjà `RTVIEW-ecran-scinde.md`. Faire tourner `UnrealBloomPass` deux fois (une par vue) doublerait son coût, qui est déjà le poste le plus cher mesuré (`quality.ts` : ~20 ms/image avec MSAA+bloom sur GPU faible). **Gain : très élevé**, évite de doubler le poste le plus cher du moteur. Source : [three.js webgl_multiple_views](https://threejs.org/examples/webgl_multiple_views.html), [Problem of continuity in multiple views with composer — three.js forum](https://discourse.threejs.org/t/problem-of-continuity-in-the-rendering-in-multiple-views-viewport-scissor-with-the-composer/70176).
3. **Ombres calculées une seule fois par image, pas par vue.** `renderer.shadowMap.autoUpdate = false` puis `renderer.shadowMap.needsUpdate = true` juste avant le rendu de la 1re vue (le shadow pass tourne à ce moment-là, pas à chaque `render()`) ; la 2e vue réutilise la même shadow map déjà calculée, elle n'a pas besoin d'un second passage. Chaque lumière qui projette une ombre est un rendu de scène complet côté GPU : avec 2 vues rendues naïvement on risque de la calculer 2×/image sans s'en rendre compte. **Gain : élevé** (directement dans le budget de RTVIEW). Sources : [renderer.shadowMap.autoUpdate — three.js forum](https://discourse.threejs.org/t/renderer-shadowmap-autoupdate-false/50401), [Add a way to trigger shadow map updates separately — three.js#23461](https://github.com/mrdoob/three.js/issues/23461).
4. **Précompiler les shaders pendant `READY?`/le menu, pas au 1er tir.** `await renderer.compileAsync(scene, camera)` (utilise l'extension `KHR_parallel_shader_compile` si dispo) pendant l'écran de sélection de map / le countdown de 3 s, pour tous les matériaux (armes, projectiles, FX d'impact, sticker 3D) qui vont apparaître en combat. Le code a déjà `installShaderWarmup` — vérifier qu'il couvre bien les matériaux de projectiles/FX de `src/scene/fx/**`, pas seulement les persos et maps. **Gain : élevé pour la démo** (évite le gel visible au 1er tir/1re explosion, le pire moment pour saccader devant le jury). Sources : [WebGLRenderer docs — compileAsync](https://threejs.org/docs/pages/WebGLRenderer.html), [Reducing shader compile time on scene initialization — three.js forum](https://discourse.threejs.org/t/reducing-shader-compile-time-on-scene-initialization/56572).
5. **Budget de 120 appels de dessin par vue = fusionner/instancer avant d'ajouter du décor.** Chaque prop de décor statique (débris, caisses, couverts d'arène LMAP2) doit passer par `InstancedMesh`/`BatchedMesh` ou un merge de géométrie plutôt qu'un mesh par objet ; Don McCurdy cite un budget classique « <100 draw calls, <100k triangles » par vue rendue — proche du budget déjà fixé par RTVIEW/PIVOT. **Gain : élevé**, c'est le levier n°1 pour les scènes avec beaucoup de props (maps Smash). Source : [100 Three.js Tips That Actually Improve Performance](https://www.utsubo.com/blog/threejs-best-practices-100-tips).
6. **Zéro allocation par frame dans la boucle de jeu/caméra.** `new THREE.Vector3()`, `new Quaternion()` etc. dans `camera/director.ts`, `movementRing.ts`, `fx/particles.ts` appelés à 60 i/s × 2 vues créent de la pression GC ; ça se voit comme des pics de frame (le fameux « stutter » périodique) plutôt qu'un FPS bas en moyenne — donc invisible sur une moyenne mais visible à l'œil en démo. Remplacer par des scratch vectors réutilisés au niveau module. **Gain : élevé sur le "jamais de saccade"** (règle #7 du CLAUDE.md), même si l'i/s moyen ne bouge pas. Source : pratique standard citée dans [Three JS Performance Guide (gist)](https://gist.github.com/iErcann/2a9dfa51ed9fc44854375796c8c24d92) et repris par les 100 tips ci-dessus.
7. **Pools d'objets pour projectiles/particules/FX d'impact.** Avec 2 joueurs qui tirent en continu (blaster en rafale de 3, grenades, throwables), créer/détruire des meshes et des `THREE.Points`/`BufferGeometry` par tir génère GC + recompilation potentielle de shader si le matériau n'est pas déjà chaud. Pré-allouer un pool fixe (ex. 30 projectiles, 200 particules) et recycler. **Gain : élevé**, directement lié au moment le plus dense de la démo (échange de tirs). Source : pattern standard, cf. gist ci-dessus et discussions pmndrs (react-three-fiber) sur le object pooling pour les particules.
8. **Ratio de pixels plafonné à 1 (voire 1,25) en écran scindé, jamais `devicePixelRatio` brut.** `rendu.pixelRatioMax` existe déjà dans `ctx.ts` — vérifier qu'il vaut 1 en mode split (2 vues = 2× le travail par pixel physique déjà). Un ratio à 2 sur un écran 1080p HiDPI quadruple le travail de fragment shader. **Gain : élevé**, quasi gratuit à vérifier/forcer. Note interne LPERF confirme déjà ce suspect prioritaire.
9. **Frustum culling par vue, pas seulement culling global.** Avec 2 caméras qui regardent des directions différentes de la même arène, s'assurer que le culling (par défaut activé par Three.js par objet, `frustumCulled = true`) n'est pas désactivé globalement par erreur (fréquent avec des shaders custom/toon `render/toon.ts`) : sinon chaque vue dessine tout le décor même hors champ. **Gain : moyen-élevé** selon la taille des arènes LMAP2 (22-28 m de diamètre, donc gain surtout si la caméra a un FOV serré).
10. **Skinning : limiter les os actifs et le nombre de `AnimationMixer` mis à jour.** 2 persos animés en simultané (KayKit skinnés) : vérifier dans `scene/fighters/animator.ts`/`animation/animator.ts` qu'un seul `mixer.update(dt)` par perso par frame (pas par vue — la vue ne doit pas redéclencher l'update), et que le nombre d'os reste dans la norme KayKit (~20-30, pas de sur-rig). **Gain : moyen**, mais facile de le casser par erreur en réutilisant le même personnage 2 fois pour 2 vues si l'update est câblé sur le rendu au lieu de la boucle physique/logique.
11. **Pas de boucle physique à la fréquence du rendu : interpoler.** Le lot LPERF signale déjà un système physique à 100 (probablement Hz fixe) dans `ctx.ts`. S'assurer que Rapier tourne à pas fixe (ex. 60 Hz) découplé du rendu, avec interpolation de position entre 2 pas physiques pour l'affichage — évite que le rendu attende la physique ou souffre d'un pas physique variable. **Gain : moyen**, surtout pour la fluidité perçue des mouvements/éjections plutôt que le FPS brut.
12. **Textures : KTX2/Basis pour les décors et stickers, jamais de PNG 2048px non compressé en VRAM.** Un PNG 2048×2048 décodé pèse ~21 Mo de VRAM une fois les mipmaps générés ; KTX2/Basis transcode vers un format GPU natif et reste compressé en mémoire (4-8× moins de VRAM), et les mipmaps sont précalculés dans le fichier au lieu d'être générés à l'exécution. Pertinent pour les stickers 3D générés par Nano Banana et les décors de maps. **Gain : moyen** (VRAM et temps de premier rendu, pas le FPS en régime stable) mais direct sur le budget « premier tour jouable < 4 s ». Sources : [Basis Universal — three.js](https://threejs.org/examples/jsm/libs/basis/), [100 Three.js Tips](https://www.utsubo.com/blog/threejs-best-practices-100-tips).
13. **Matériaux partagés entre instances identiques (armes, projectiles du même type, débris de map).** Éviter un `MeshStandardMaterial` cloné par instance (ça casse aussi le batching/instancing du point 5 et force plus de programmes shader uniques = plus de compilations). Vérifier `src/scene/maps/materials.ts` et le pipeline de sticker 3D. **Gain : moyen**, complète directement le point 5.
14. **HUD : ne jamais réécrire le DOM à chaque frame (mise en page forcée).** Le HUD scindé (2 barres de vie/%, cooldowns d'armes, anneau de parade) mis à jour à 60 i/s doit passer par `textContent`/`style.transform` ciblés (jamais `innerHTML` complet) et éviter les lectures de layout (`getBoundingClientRect`) dans la boucle de rendu — sinon on force un reflow synchrone qui bloque le thread principal, donc les 2 vues. Signalé comme suspect explicite dans `LPERF-fluidite.md`. **Gain : moyen**, facile à rater avec un HUD scindé qui double le nombre d'éléments à mettre à jour.
15. **Chargement audio à la demande plutôt que 252 voix préchargées, `vite build` pour la démo.** Déjà identifié dans `LPERF-fluidite.md` : précharger toutes les voix bloque/alourdit le démarrage inutilement (pas le FPS en combat, mais le temps avant que le jeu soit jouable). `npm run demo` (`vite build && vite preview`) obligatoire pour juger le FPS réel — le serveur dev sert des modules non groupés, nettement plus lent, ce qui fausserait toute mesure faite avant la démo. **Gain : moyen mais critique pour ne pas se tromper de diagnostic** — mesurer en dev donnerait de faux positifs partout ailleurs dans cette liste.

## 2. Protocole de mesure reproductible (Playwright + `window.gameHooks`)

**Build à mesurer :** toujours `npm run demo` (build de prod + `vite preview`), jamais le serveur dev — sinon toute mesure est faussée (règle #15).

**Lancement Chromium avec GPU réel** (le mode headless utilise SwiftShader, logiciel, inutilisable pour du FPS) :
```js
chromium.launch({
  headless: false,
  args: ['--use-angle=d3d11', '--ignore-gpu-blocklist', '--enable-gpu-rasterization', '--force_high_performance_gpu'],
});
// viewport 1920x1080, deviceScaleFactor = celui de la machine de démo
```

**Séquence de test (scriptée via `window.gameHooks`, identique sur les 3 maps) :**
1. `startMatch({ mapId, split: true })` avec `setSeed` fixe.
2. Skip/accélérer le `countdown` (`?demo=1` ou hook dédié).
3. 20 s de « les 2 joueurs courent » : `input(1, 'move', ...)` + `input(2, 'move', ...)` en continu (bouger, sauter, longer les bords).
4. 10 s de « tirs croisés » : les 2 joueurs tirent en rafale (blaster), au moins une grenade et un throwable de chaque côté, au moins une parade parfaite déclenchée.
5. Déclencher au moins 2 explosions/impacts qui font apparaître des FX (nouveaux matériaux = risque de compilation à chaud).
6. `forcerVictoire` pour déclencher un KO (zoom KO, ralenti, écran de fin).

**Ce qu'on mesure, en continu pendant toute la séquence :**
- i/s instantané par frame (`requestAnimationFrame` delta) → **i/s moyen** et **1 % low** (moyenne du 1 % de frames les plus lentes, pas juste le minimum, pour ignorer un seul pic isolé).
- **pire image** (ms) sur toute la séquence, avec l'action qui s'y déroulait (log de la phase de jeu à ce timestamp).
- `PerformanceObserver('longtask')` : nombre et durée des tâches longues (>50 ms) sur le thread principal pendant les 30 s.
- `renderer.info.render.calls`, `.triangles`, `.frame` **par vue** (relever juste avant/après chaque `render()` de vue, ou lire `renderer.info` après un `reset()` ciblé si dispo) — comparer aux 120 appels/vue du budget.
- `renderer.info.memory.textures/geometries` + `performance.memory.usedJSHeapSize` (Chrome) avant/après les 30 s, pour repérer une fuite.
- Comptage des compilations de shaders pendant le combat (patcher temporairement `WebGLProgram`/écouter les warnings, ou vérifier qu'aucune frame de la séquence 4-5 ne dépasse le seuil pendant une action censée être déjà préchauffée).
- Temps entre le clic « PLAY »/choix de map et le premier tour jouable (`countdown` terminé), et taille/temps réseau des assets chargés dans cette fenêtre (GLB, textures, voix).
- Latence des appels `/api/*` (scan objet, sticker, commentaire, TTS) et si l'écran se bloque (aucune frame rendue) pendant l'attente — à tester en particulier au moment du scan d'objet et de la caisse Snap.

**Seuils d'acceptation (alignés sur `LPERF-fluidite.md` et `PIVOT-TEMPS-REEL.md`) :**
- i/s moyen ≥ 58, **1 % low ≥ 50 i/s**, sur les 3 maps, en écran scindé, avec la séquence complète ci-dessus.
- Aucune frame > 50 ms pendant tout le match (donc aucune longtask > 50 ms visible côté rendu).
- ≤ 120 appels de dessin par vue.
- Aucune compilation de shader détectée pendant les phases 4-6 (tout doit être préchauffé pendant le countdown/menu).
- Premier tour jouable < 4 s après le choix de map.
- Aucun blocage de frame > 1 image pendant un appel `/api/*` (doit être asynchrone, jamais sur le thread de rendu).

## 3. Les 5 points les plus risqués repérés dans le code existant

1. **`src/scene/render/postfx.ts`** : le composeur actuel (`RenderPass` → `UnrealBloomPass` → `ShaderPass` étalonnage → `OutputPass`) est câblé pour **une seule caméra/scène** (`installPostFx` prend `ctx.three.camera` unique et remplace `ctx.three.render`). Le passage à 2 vues doit impérativement garder un seul passage de post-traitement sur l'image complète (règle #2) — c'est exactement le risque que `RTVIEW-ecran-scinde.md` anticipe déjà (« s'il ne s'adapte pas proprement, désactive le bloom en mode scindé »). À vérifier en priorité une fois RTVIEW livré.
2. **`src/core/ctx.ts`** : la boucle de rendu (`loop.addSystem('render', ...)`) ne connaît aujourd'hui qu'une seule `camera`/`scene`, et le mode « qualité basse » bascule sur un rendu direct sans composeur. Il faut s'assurer que le rendu 2-vues respecte aussi ce garde-fou qualité basse (sinon un GPU faible en écran scindé n'a aucune échappatoire et tombe sous 30 i/s pendant la démo).
3. **`quality.ts`** : la mesure de qualité auto se déclenche sur `phase:change` vers `move/countdown/fight`, avec une fenêtre de mesure de 2,5 s après 1,5 s d'attente — en écran scindé le coût double d'un coup dès `fight` (2 vues au lieu d'1), donc cette bascule doit re-mesurer spécifiquement en mode split, pas réutiliser une mesure faite en solo/menu. Risque de rester bloqué en « haute » qualité alors que le split la fait chuter sous le seuil.
4. **Shaders des FX** (`src/scene/fx/impact.ts`, `fx/particles.ts`, `fx/smash/index.ts`) : `installShaderWarmup` existe mais il faut vérifier qu'il couvre bien tous les matériaux d'impact/FX de combat et pas seulement les persos/maps — sinon la 1re explosion ou la 1re parade parfaite du match (moment fort de la démo) déclenche une compilation à la volée et une saccade visible devant le jury.
5. **HUD scindé** (`src/ui/**`, hors du périmètre RTVIEW mais impacté) : le HUD double son nombre d'éléments à mettre à jour à 60 i/s (barres de %, cooldowns, anneau de parade par joueur) ; le point 14 de la liste (pas de réécriture DOM/reflow forcé par frame) devient deux fois plus risqué qu'en tour par tour, où le HUD ne changeait qu'entre les tours.

## 4. Grille d'évaluation /10 pour un agent critique « perf »

| Critère | Points | Ce qui vaut le maximum |
|---|---|---|
| i/s moyen et 1 % low mesurés en conditions réelles (`npm run demo`, GPU NVIDIA forcé, écran scindé, séquence complète) | 2 | ≥ 58 i/s moyen et ≥ 50 i/s en 1 % low sur les 3 maps |
| Aucune image > 50 ms pendant tout un match scripté | 2 | 0 frame au-delà du seuil sur toute la séquence de mesure (course + tirs + explosions + KO) |
| Appels de dessin par vue dans le budget | 1 | ≤ 120 appels/vue mesurés via `renderer.info` |
| Post-traitement à une seule passe pour les 2 vues | 1 | Bloom/vignette/étalonnage appliqués une seule fois sur l'image composée, jamais dupliqués par vue |
| Shaders préchauffés avant le combat | 1 | Zéro compilation détectée pendant les phases de tir/impact/KO du script de mesure |
| Premier tour jouable rapide | 1 | < 4 s entre le choix de map et la fin du countdown |
| Pas de fuite mémoire / GC visible | 1 | Mémoire JS stable sur 2 min de match répété, pas de pic de frame périodique lié à l'allocation |
| Appels IA (`/api/*`) non bloquants | 1 | Aucune frame de rendu sautée pendant un appel scan/sticker/commentaire/TTS |

**Note finale = somme des points obtenus** (0 à 10). Seuil de refus aligné sur `critique-aaa` : sous 8 après 15h, une relance ; sous 8 deux fois de suite sur le même point → l'humain tranche (règle CLAUDE.md).
